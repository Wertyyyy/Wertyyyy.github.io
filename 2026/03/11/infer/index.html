When profiling an LLM in production, one of the most important questions an engineer can ask is: is this kernel bottlenecked by compute or by memory bandwidth? The answer dictates which hardware specs to chase, which algorithmic tricks will actually help, and ultimately how much each generated token costs.

The key quantity that answers this question is arithmetic intensity — the number of floating-point operations performed per byte of data moved between compute cores and High Bandwidth Memory (HBM). We write it as ops:byte:

ops:byte  ≜  FLOPsBytes accessed from HBM\text{ops:byte} \;\triangleq\; \frac{\text{FLOPs}}{\text{Bytes accessed from HBM}} ops:byte≜Bytes accessed from HBMFLOPs​

Every GPU has a hardware balance point: the ops:byte ratio at which compute throughput and memory bandwidth are equally saturated. Operations whose arithmetic intensity falls below this threshold are memory-bound — the GPU idles waiting for data. Operations above it are compute-bound — the GPU computes faster than data arrives.

In this post we derive the arithmetic intensity for every major component of Transformer inference: attention in both the prefill and decode phases, and the feed-forward network. We then connect these results to the practical metrics TTFT and TPOT.

Reference: Baseten — LLM Transformer Inference Guide

1. The Hardware Balance Point

Before diving into formulas, it helps to anchor the analysis with concrete GPU numbers. The ops:byte of a GPU is simply its peak FLOP/s divided by its peak HBM bandwidth.

GPU BF16 Peak (TFLOP/s) HBM Bandwidth (TB/s) ops:byte
RTX 4090 330 1.0 330
A100 SXM4 312 2.0 156
H20 148 4.0 37

Note: ops:byte is derived directly as (Peak FLOP/s) / (Peak Bandwidth). Since numerator and denominator are already in consistent units (FLOP/s and Byte/s), no additional factor for the 2-byte width of BF16 elements is needed.

The ops:byte column defines the roofline: any kernel with arithmetic intensity below this value is memory-bandwidth-limited, no matter how powerful the compute units are. We will see that different inference phases land on very different points of this roofline.

2. GEMM FLOPs: A Quick Primer

Every quantity derived later reduces to counting floating-point operations in one or more matrix multiplications (GEMMs). It is worth deriving the general formula carefully, since a small notational slip is the most common source of errors.

2.1 General Formula

Given A∈Rm×k\mathbf{A} \in \mathbb{R}^{m \times k}A∈Rm×k and B∈Rk×n\mathbf{B} \in \mathbb{R}^{k \times n}B∈Rk×n, the product C=AB∈Rm×n\mathbf{C} = \mathbf{A}\mathbf{B} \in \mathbb{R}^{m \times n}C=AB∈Rm×n has mnmnmn output elements. Each element is the inner product of a row of A\mathbf{A}A with a column of B\mathbf{B}B:

cij=∑l=1kail bljc_{ij} = \sum_{l=1}^{k} a_{il}\, b_{lj} cij​=l=1∑k​ail​blj​

This requires kkk multiplications and k−1k-1k−1 additions, for a total of 2k−1≈2k2k - 1 \approx 2k2k−1≈2k floating-point operations per element. Summing over all mnmnmn elements:

FLOPs(AB)=2mnk\boxed{\text{FLOPs}(\mathbf{A}\mathbf{B}) = 2mnk} FLOPs(AB)=2mnk​

The key observation is that the FLOPs scale with the product of all three dimensions mmm, nnn, kkk — the two “outer” dimensions of the output and the “inner” (contraction) dimension.

3. Prefill: Attention Arithmetic Intensity

When a prompt of length SSS is processed, all SSS tokens are attended to simultaneously. This is the prefill phase.

Let BBB be the batch size, HHH the number of attention heads, SSS the sequence length, and DHD_HDH​ the per-head dimension. The query, key, value, and output tensors are:

Q, K, V, O  ∈  RB×H×S×DH\mathbf{Q},\, \mathbf{K},\, \mathbf{V},\, \mathbf{O} \;\in\; \mathbb{R}^{B \times H \times S \times D_H} Q,K,V,O∈RB×H×S×DH​

All tensors are stored in BF16 (2 bytes per element). We analyze a single attention head first, then scale by BHBHBH.

3.1 FLOPs

The core computation of scaled dot-product attention for a single head involves two matrix multiplications:

QKT:[S, DH]×[DH, S]  ⟶  [S, S],FLOPs=2S2DH\mathbf{Q}\mathbf{K}^{\mathsf{T}}:\quad [S,\, D_H] \times [D_H,\, S] \;\longrightarrow\; [S,\, S], \qquad \text{FLOPs} = 2S^2 D_H QKT:[S,DH​]×[DH​,S]⟶[S,S],FLOPs=2S2DH​

softmax(QKT) V:[S, S]×[S, DH]  ⟶  [S, DH],FLOPs=2S2DH\text{softmax}(\mathbf{Q}\mathbf{K}^{\mathsf{T}})\,\mathbf{V}:\quad [S,\, S] \times [S,\, D_H] \;\longrightarrow\; [S,\, D_H], \qquad \text{FLOPs} = 2S^2 D_H softmax(QKT)V:[S,S]×[S,DH​]⟶[S,DH​],FLOPs=2S2DH​

Per head: 4S2DH4S^2 D_H4S2DH​ FLOPs. Scaled to all BBB batches and HHH heads:

FLOPsprefill=4BHS2DH\boxed{\text{FLOPs}_{\text{prefill}} = 4BHS^2 D_H} FLOPsprefill​=4BHS2DH​​

Softmax and scaling contribute O(S2)O(S^2)O(S2) FLOPs but with a much smaller constant, so we absorb them into the leading term.

3.3 Arithmetic Intensity

Without FlashAttention:

ops:byteprefill naive=4BHS2DH8BHSDH+4BHS2=SDH2DH+S\text{ops:byte}_{\text{prefill}}^{\,\text{naive}} = \frac{4BHS^2D_H}{8BHSD_H + 4BHS^2} = \frac{SD_H}{2D_H + S} ops:byteprefillnaive​=8BHSDH​+4BHS24BHS2DH​​=2DH​+SSDH​​

As S→∞S \to \inftyS→∞ this saturates at DHD_HDH​ (typically 64–128). Long prompts therefore push naive prefill toward the compute-bound regime.

With FlashAttention:

ops:byteprefill FA=4BHS2DH4BHSDH ⁣(1+ST)=S1+ST=STS+T\text{ops:byte}_{\text{prefill}}^{\,\text{FA}} = \frac{4BHS^2D_H}{4BHSD_H\!\left(1 + \dfrac{S}{T}\right)} = \frac{S}{1 + \dfrac{S}{T}} = \frac{ST}{S + T} ops:byteprefillFA​=4BHSDH​(1+TS​)4BHS2DH​​=1+TS​S​=S+TST​

For large SSS this converges to TTT rather than DHD_HDH​. FlashAttention’s real advantages are therefore elsewhere:

  1. Eliminates the O(BHS2)O(BHS^2)O(BHS2) HBM allocation. The score matrix A\mathbf{A}A is never materialized, making long-context inference feasible and dramatically reducing peak VRAM.

  2. Avoids compute–memory pipeline stalls. In the unfused implementation the two GEMMs are serialized through HBM: GEMM1 (QKT\mathbf{Q}\mathbf{K}^{\mathsf{T}}QKT) writes A\mathbf{A}A to HBM, then the GPU stalls until that write completes and the softmax kernel re-reads A\mathbf{A}A, and only then does GEMM2 (softmax(A)V\text{softmax}(\mathbf{A})\mathbf{V}softmax(A)V) begin. Each HBM round-trip is dead time on the compute units. FlashAttention fuses QKT\mathbf{Q}\mathbf{K}^{\mathsf{T}}QKT, softmax, and AV\mathbf{A}\mathbf{V}AV into a single tiled kernel that keeps all intermediate values in SRAM — so the compute pipeline never stalls waiting for HBM, and compute and memory transfers are maximally overlapped across tiles.

4. Decode: Attention Arithmetic Intensity

After processing the prompt, the model generates one new token per step. Each decode step attends the single new query against all previously seen keys and values stored in the KV cache. This is the decode phase.

Let StotalS_{\text{total}}Stotal​ be the current KV cache length (prompt tokens plus all tokens generated so far). The shapes become:

Q∈RB×H×1×DH,K, V∈RB×H×Stotal×DH\mathbf{Q} \in \mathbb{R}^{B \times H \times 1 \times D_H}, \qquad \mathbf{K},\, \mathbf{V} \in \mathbb{R}^{B \times H \times S_{\text{total}} \times D_H} Q∈RB×H×1×DH​,K,V∈RB×H×Stotal​×DH​

4.1 FLOPs

For a single head, the two matrix multiplications are:

QKT:[1, DH]×[DH, Stotal]  ⟶  [1, Stotal],FLOPs=2DHStotal\mathbf{Q}\mathbf{K}^{\mathsf{T}}:\quad [1,\, D_H] \times [D_H,\, S_{\text{total}}] \;\longrightarrow\; [1,\, S_{\text{total}}], \qquad \text{FLOPs} = 2D_H S_{\text{total}} QKT:[1,DH​]×[DH​,Stotal​]⟶[1,Stotal​],FLOPs=2DH​Stotal​

An ops:byte of 1 is far below every GPU’s hardware balance point (37 on the H20, 156 on the A100, 330 on the RTX 4090). Decode attention is severely memory-bandwidth-limited on all current hardware, regardless of sequence length.

5. Feed-Forward Networks

The FFN operates token-wise with no cross-token interaction and no dependence on the KV cache. We analyze both the classic two-layer variant and the gated variant used in modern LLMs. All data is BF16 (2 bytes per element).

5.1 ReLU FFN

XW1:  (m,n,k)=(BS, Dff, D)  ⟹  2⋅BS⋅Dff⋅D\mathbf{X}\mathbf{W}_1:\; (m, n, k) = (BS,\, D_{\text{ff}},\, D) \;\Longrightarrow\; 2 \cdot BS \cdot D_{\text{ff}} \cdot D XW1​:(m,n,k)=(BS,Dff​,D)⟹2⋅BS⋅Dff​⋅D

Contrast this with attention, where QKT\mathbf{Q}\mathbf{K}^{\mathsf{T}}QKT has shape [S,DH]×[DH,S][S, D_H] \times [D_H, S][S,DH​]×[DH​,S], producing S2S^2S2 output elements each requiring DHD_HDH​ operations — a quadratic S2DHS^2 D_HS2DH​ scaling that has no analogue in the FFN.

5.2 SwiGLU / GeGLU FFN

Modern LLMs (LLaMA, Mistral, Gemma, etc.) replace the standard FFN with a gated variant:

Y=W3(σ(W1X)⊙(W2X)),W1, W2∈RD×Dff,W3∈RDff×D\mathbf{Y} = \mathbf{W}_3\bigl(\sigma(\mathbf{W}_1\mathbf{X}) \odot (\mathbf{W}_2\mathbf{X})\bigr), \qquad \mathbf{W}_1,\, \mathbf{W}_2 \in \mathbb{R}^{D \times D_{\text{ff}}},\quad \mathbf{W}_3 \in \mathbb{R}^{D_{\text{ff}} \times D} Y=W3​(σ(W1​X)⊙(W2​X)),W1​,W2​∈RD×Dff​,W3​∈RDff​×D

where σ\sigmaσ is the Swish activation (SwiGLU) or GELU (GeGLU), and ⊙\odot⊙ is the element-wise product.

FLOPs. There are now three GEMMs. Applying 2mnk2mnk2mnk to each:

6. Putting It All Together

Component Phase ops:byte Bottleneck
Attention (naive) Prefill DHD_HDH​ Compute
Attention (FA) Prefill TTT —
Attention Decode 111 Memory bandwidth
FFN Prefill 1.2D1.2D1.2D Compute
FFN Decode 111 Memory bandwidth

The central insight is a clean split: prefill is (approximately) compute-bound; decode is always memory-bandwidth-bound. This asymmetry is fundamental, not accidental — decode attention must read the entire KV cache for every new token, and the number of useful FLOPs that comes with that read is exactly O(1)O(1)O(1) per byte. The same logic applies to single-token FFN passes: the weight matrices must be streamed from HBM, but each element contributes only one multiply-add.

This asymmetry has a direct engineering consequence: the GPU best suited for prefill is not the same one best suited for decode. A compute-heavy GPU (e.g., RTX 4090, ops:byte = 330) idles during decode waiting for KV-cache data; a bandwidth-heavy GPU (e.g., H20, ops:byte = 37) wastes its compute during prefill since prefill AI already exceeds its balance point.

Disaggregated prefill-decode (PD disaggregation) resolves this by running each phase on purpose-suited hardware: the 4090 ingests the prompt and transfers the resulting KV cache over the interconnect; the H20 streams it at full 4.0 TB/s to emit tokens. Each GPU operates near its own roofline — each doing what physics designed it to do.

7. Metrics: TTFT, TPOT and ITL

The prefill/decode asymmetry maps directly onto the standard latency metrics used in LLM serving:

Metric Full name What it measures Dominated by
TTFT Time To First Token Time from request submission to the first output token Prefill
TPOT Time Per Output Token Average time per token across a full response Decode
ITL Inter-Token Latency Time between consecutive output tokens in a live request Decode (+ prefill interference)

TTFT reflects how fast the model ingests the prompt. Prefill processes all SSS tokens in parallel and has arithmetic intensity approaching DHD_HDH​ for long sequences — it is near-compute-bound, so TTFT scales roughly with prompt length and benefits from high TFLOP/s GPUs.

TPOT reflects average per-token generation speed measured over a complete response. Because every decode step is severely memory-bandwidth-limited (ops:byte ≈ 1), TPOT is governed primarily by HBM bandwidth, not peak TFLOP/s. This is why a high-bandwidth GPU like the H20 (4.0 TB/s) often achieves lower TPOT than nominally faster compute GPUs, despite its lower TFLOP/s rating.

ITL measures the instantaneous gap between consecutive output tokens from the perspective of a single in-flight request. Under a pure dedicated decode workload, ITL ≈ TPOT. However, in a continuous-batching system that co-schedules prefill and decode on the same GPU, a long new-request prefill monopolizes the GPU for one full step and stalls all active decode streams — causing a temporary ITL spike proportional to the prompt length SSS.

Chunked prefill (available in vLLM and SGLang) addresses this interference directly. Instead of running a full prompt in one step, the prompt is split into fixed-size chunks of CCC tokens. Each GPU step processes one chunk of prefill tokens alongside all pending decode tokens:

tokens per step=min⁡(Sremaining, C)⏟prefill chunk+Bdecode⏟active decode batch\text{tokens per step} = \underbrace{\min(S_{\text{remaining}},\, C)}_{\text{prefill chunk}} + \underbrace{B_{\text{decode}}}_{\text{active decode batch}} tokens per step=prefill chunkmin(Sremaining​,C)​​+active decode batchBdecode​​​

This converts a single large ITL spike into many small ones, smoothing the token stream for concurrent users at the cost of slightly increased TTFT for the requesting client.

In PD-disaggregated deployments this trade-off disappears entirely: decode nodes never share a GPU with prefill computation, so ITL reduces to a pure function of HBM bandwidth with no interference spikes. This is, in a sense, the ultimate conclusion of the arithmetic-intensity argument — disaggregation does not merely improve average throughput, it removes an entire class of latency variability.
