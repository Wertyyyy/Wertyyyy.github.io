The VRAM consumed by an LLM composed of decoder-only transformer blocks during training can generally be divided into the following parts:

Category Without AMP With AMP
Parameters 4P4P4P –
Gradients 4P4P4P 2P2P2P
Optimizer 8P8P8P 12P12P12P
Activations ∝BSD\propto BSD∝BSD ∝BSD\propto BSD∝BSD

Note 1: for optimizers, AdamW and similar methods need to store the momentum and second moment (variance) of the parameters. When AMP is used, an additional FP32 copy of the parameters is also stored to maintain numerical stability.

Note 2: Although we often assume that training keeps both the BF16 parameters and an FP32 parameter copy at the same time, in practice, at least in FSDP2, only the FP32 parameters are kept.

Parameters, gradients, and optimizer states are tied to the parameter count and are relatively easy to analyze. Activations, however, depend on the number of input tokens and are harder to characterize. We analyze this part in detail in the next section.

Given an input X∈RB,S,D\mathbf{X} \in \mathbb{R}^{B, S, D}X∈RB,S,D, and because RMSNorm is a token-wise normalization method, we consider each token x∈RDx \in \mathbb{R}^{D}x∈RD separately:

  1. Compute the root mean square:

    RMS(x)=1D∑i=1Dxi2+ϵ∈R\text{RMS}(x) = \sqrt{\frac{1}{D} \sum_{i=1}^{D} x_i^2 + \epsilon} \in \mathbb{R} RMS(x)=D1​i=1∑D​xi2​+ϵ​∈R

    Extending this operation to the full input tensor X\mathbf{X}X gives RMS(X)∈RB,S,1\text{RMS}(\mathbf{X}) \in \mathbb{R}^{B, S, 1}RMS(X)∈RB,S,1, where the singleton dimension is typically kept for broadcasting.

  2. Normalize:

    x^=xRMS(x)∈RD\begin{align*} \hat{x} &= \frac{x}{\text{RMS}(x)} \in \mathbb{R}^{D} \end{align*} x^​=RMS(x)x​∈RD​

    Extending this to the full input tensor X\mathbf{X}X gives X^∈RB,S,D\hat{\mathbf{X}} \in \mathbb{R}^{B, S, D}X^∈RB,S,D.

  3. Scale with γ∈RD\gamma \in \mathbb{R}^{D}γ∈RD:

    y=x^⊙γ∈RDy = \hat{x} \odot \gamma \in \mathbb{R}^{D} y=x^⊙γ∈RD

    Extending this to the full tensor X^\hat{\mathbf{X}}X^ gives Y∈RB,S,D\mathbf{Y} \in \mathbb{R}^{B, S, D}Y∈RB,S,D.

Based on the computation graph above, we can analyze which intermediate forward tensors (activations) must be saved during backpropagation:

  1. Intermediate division (normalization) X^=XRMS(X)\hat{\mathbf{X}} = \frac{\mathbf{X}}{\text{RMS}(\mathbf{X})}X^=RMS(X)X​:
    To backpropagate gradients with respect to the input X\mathbf{X}X, the derivative formula uses both X\mathbf{X}X itself and RMS(X)\text{RMS}(\mathbf{X})RMS(X). Therefore, we need to retain X\mathbf{X}X and RMS(X)\text{RMS}(\mathbf{X})RMS(X).

    • RMS(X)\text{RMS}(\mathbf{X})RMS(X) has shape [B,S,1][B, S, 1][B,S,1], which is tiny compared with the main tensor and can almost be ignored.

  2. Final multiplication (scaling) Y=X^⊙γ\mathbf{Y} = \hat{\mathbf{X}} \odot \gammaY=X^⊙γ:
    To compute the gradient with respect to γ\gammaγ, we need the formula ∂L∂γ=∑(∂L∂Y⊙X^)\frac{\partial L}{\partial \gamma} = \sum \left( \frac{\partial L}{\partial \mathbf{Y}} \odot \hat{\mathbf{X}} \right)∂γ∂L​=∑(∂Y∂L​⊙X^). Therefore, in theory we need to save the normalized tensor X^∈RB,S,D\hat{\mathbf{X}} \in \mathbb{R}^{B, S, D}X^∈RB,S,D.

    • Because X^=XRMS(X)\hat{\mathbf{X}} = \frac{\mathbf{X}}{\text{RMS}(\mathbf{X})}X^=RMS(X)X​ is cheap to compute, and because backpropagation already needs the input X\mathbf{X}X (which is usually saved by the preceding operator), modern deep learning frameworks typically save only the input X\mathbf{X}X and the corresponding RMS(X)\text{RMS}(\mathbf{X})RMS(X) (or its reciprocal).

Conclusion: In a standard RMSNorm implementation, the main activation that needs to be retained is only the input layer X∈RB,S,D\mathbf{X} \in \mathbb{R}^{B, S, D}X∈RB,S,D.

    Y=OWO∈RB,S,D\begin{align*} \mathbf{Y} &= \mathbf{O} \mathbf{W}_O \in \mathbb{R}^{B, S, D} \end{align*} Y​=OWO​∈RB,S,D​

Attention involves two kinds of operations:

  • Matrix multiplication: to support backward computation, both input tensors must be saved.
  • Softmax:
    • In a naive implementation, the output tensor must be saved for backward computation.
    • In some optimized implementations, such as Flash Attention, the softmax output is avoided by saving the maximum value and the sum of exponentials as statistics and recomputing as needed.

Empirical Results

Experimental Setup

We conducted a systematic ablation study based on the FSDP2 framework along two dimensions: CPU Offload and Activation Checkpointing (AC). The following five configurations were evaluated:

Configuration CPU Offload Activation Checkpointing
+offload +checkpointing +layerac ✓ layer-wise
+offload +checkpointing ✓ submodule-wise
+offload −checkpointing ✓ submodule-wise
+checkpointing −offload ✗ submodule-wise
−offload −checkpointing ✗ submodule-wise

Here, CPU Offload moves parameters, optimizer states, and gradients to CPU memory and all-gathers them back to the GPU on demand before computation, eliminating their fixed VRAM footprint. Activation Checkpointing comes in two granularities:

  • layer-wise: treat the entire Decoder Layer as one checkpoint unit, keeping only each layer’s input X\mathbf{X}X; all intermediate activations inside Norm / Attention / FFN are recomputed during backpropagation.
  • submodule-wise: treat each submodule inside a Decoder Layer (RMSNorm, Attention, RMSNorm, FFN) as an independent checkpoint unit, keeping only its own input. This is finer-grained and reduces the recomputation scope.

The difference between these two granularities is very clear in the code. Below is the core implementation snippet from the accelerate library:

auto_wrap_policy_func is based on FSDP’s auto_wrap_policy and is used to decide whether a module is a “sharding unit”. For a standard LLM, this usually corresponds exactly to one complete Decoder Layer.

  • submodule-wise (if auto_wrap_policy_func(parent_module)): when iterating over each submodule, the code checks whether its parent module matches the policy. A match means the current submodule is a direct child of some Decoder Layer, that is, one of RMSNorm / Attention / RMSNorm / FFN. Each of these submodules is therefore wrapped independently with checkpoint_wrapper, achieving submodule-level checkpointing.
  • layer-wise (if auto_wrap_policy_func(layer), shown as a comment): during traversal, the code instead checks whether the current module itself matches the policy. A match means the current module is the Decoder Layer itself, so the entire Decoder Layer is wrapped as one checkpoint unit.

Before running the experiments, we first organize the model’s key parameters to serve as a reference baseline for the later analysis.

Fixed VRAM related to parameter count

Qwen2.5-3B-Instruct has a total parameter count of about 3.09B. After the forward pass ends, no gradients exist yet. With AMP (BF16 parameters + FP32 optimizer), each parameter requires 12 bytes (FP32 Adam first moment, second moment, and FP32 master parameter copy). Averaged over 8 GPUs:

12×3.09×1098×10243≈4.32GB\frac{12 \times 3.09 \times 10^9}{8 \times 1024^3} \approx 4.32 \text{GB} 8×1024312×3.09×109​≈4.32GB

Note: although BF16 parameters and FP32 parameter copies are usually assumed to coexist, experiments show that in practice only the FP32 parameters are retained.

Data Analysis

We first analyze the VRAM snapshot at the end of each batch’s forward pass (forward_end). This point is chosen because the state is the cleanest: the forward pass has completed and all activations have been written to memory; backpropagation has not yet started, so gradient tensors have not been allocated. At this point, VRAM contains only parameters + optimizer states (fixed terms) and the full activations for the current batch (which grow linearly with token count), making the intercept and slope easy to interpret and directly compare with theory.

From the plot, it is clear that the VRAM usage under all five configurations is strongly linear in the input token count, exactly matching the theoretical analysis: activation cost is proportional to the number of tokens NNN, while parameters and optimizer states are constants. Together, these determine the slope and intercept of the linear function.

Locating the Activations

To locate the source of this extra VRAM, we captured CUDA memory snapshots during the experiment and visualized them with the memory_viz tool. Each GPU handled 3920 tokens in the experiment.

The figure shows all resident activation tensors within a single layer. The most prominent features are four large blocks and the first smaller block immediately below them, which together account for the FFN activation cost of BSD+4×BSDffBSD + 4 \times BSD_{ff}BSD+4×BSDff​.

Each of the four large blocks occupies 83.1 MiB, corresponding to BSDffBSD_{ff}BSDff​, and the smaller block directly below them is 15.5 MiB, corresponding to BSDBSDBSD. Using BF16 precision (2 bytes per element), N=B×SN = B \times SN=B×S tokens per GPU, D=2048D = 2048D=2048, and Dff=⌊5.37D⌋=11008D_{ff} = \lfloor 5.37D \rfloor = 11008Dff​=⌊5.37D⌋=11008, with N=3920N = 3920N=3920:

BSD=2×3920×204810242≈15.3 MiBBSD = \frac{2 \times 3920 \times 2048}{1024^2} \approx 15.3\,\text{MiB} BSD=102422×3920×2048​≈15.3MiB

BSDff=2×3920×1100810242≈82.3 MiBBSD_{ff} = \frac{2 \times 3920 \times 11008}{1024^2} \approx 82.3\,\text{MiB} BSDff​=102422×3920×11008​≈82.3MiB

These values match the 15.5 MiB and 83.1 MiB observed in the snapshot very closely.

The remaining part can be divided into three regions: the central Attention region contains X\mathbf{X}X, Q\mathbf{Q}Q, and O\mathbf{O}O (each 15.5 MiB), as well as the smaller K\mathbf{K}K and V\mathbf{V}V (each 1.9 MiB); the upper and lower regions are two RMSNorm blocks. In theory, each RMSNorm only needs to save 1×BSD1 \times BSD1×BSD (that is, 15.5 MiB). However, the visualization shows that each RMSNorm actually saves 3×BSD3 \times BSD3×BSD: one 31 MiB FP32 tensor and one 15.5 MiB BF16 tensor. To locate the source of these two extra tensors, we inspected the model source code:

The extra cost comes from the precision conversions on lines 198 and 201. RMSNorm requires higher numerical precision when computing the variance. If the squared mean were computed directly in BF16, accumulated error would shift the variance estimate and affect the normalization result. The implementation therefore first casts the input up to FP32 for computation (line 198), and then casts it back down to the original precision for output (line 201). This design creates two additional resident tensors at the PyTorch autograd level:

  • Line 198: hidden_states.to(torch.float32) creates an FP32 tensor. The subsequent pow(2).mean() and uses this tensor as input, and autograd must keep it for the backward pass of the variance computation. Its size is equivalent to 2×BSD2 \times BSD2×BSD (FP32 precision, which is twice the size of a BF16 tensor).
  • Line 201: in self.weight * hidden_states.to(input_dtype), .to(input_dtype) first creates a BF16 intermediate tensor; autograd needs to retain this tensor to compute the gradient of self.weight, and its size is 1×BSD1 \times BSD1×BSD.

Both tensors come from Norm 1 (labeled in the snapshot as Norm 1 Tensor 1 / FP32 and Norm 1 Tensor 2 / BF16), and the two RMSNorm blocks behave symmetrically. In the memory snapshot, the two tensors saved by each RMSNorm can be observed directly:

  • Norm X Tensor 1 / FP32 (31 MiB): the FP32 tensor created by the upcast on line 198, occupying 2×BSD2 \times BSD2×BSD;
  • Norm X Tensor 2 / BF16 (15.5 MiB): the BF16 intermediate tensor created by the type cast on line 201, occupying 1×BSD1 \times BSD1×BSD.

Each RMSNorm actually saves 3×BSD3 \times BSD3×BSD rather than the theoretically expected 1×BSD1 \times BSD1×BSD, so each RMSNorm introduces an additional 2×BSD2 \times BSD2×BSD of overhead. Since each layer contains two RMSNorm blocks, the excess per layer is 4BSD4 BSD4BSD, which fully explains the VRAM discrepancy.
